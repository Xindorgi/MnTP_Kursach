# 1. Аналитическая часть

## 1.1 Обзор предметной области

Сокращение URL (англ. URL shortening) — это техника преобразования длинного интернет-адреса в компактный короткий код, который перенаправляет пользователя на исходный ресурс. Короткие ссылки широко используются в социальных сетях, мессенджерах, email-рассылках и печатных материалах, где длина ссылки имеет значение. Помимо очевидного сокращения длины, сервисы сокращения ссылок предоставляют возможность сбора аналитики переходов: количество кликов, география пользователей, источники трафика, временная разбивка.

Основные области применения сервисов сокращения ссылок:

- **Маркетинг и реклама** — отслеживание эффективности рекламных кампаний, анализ переходов по разным каналам (социальные сети, email, контекстная реклама).
- **Социальные сети и мессенджеры** — размещение ссылок в условиях ограниченной длины сообщения (Twitter/X, SMS).
- **Брендинг** — создание коротких запоминающихся ссылок с собственным доменом (брендированные короткие ссылки).
- **Аналитика контента** — сбор статистики распространения материалов, определение популярности публикаций.
- **Безопасность** — маскировка длинных URL с параметрами, фильтрация вредоносных ссылок через проверку при редиректе.

Ключевые механизмы работы сервиса сокращения ссылок включают:

- **Генерация короткого кода** — преобразование числового идентификатора записи в короткую строку с использованием алгоритмов вроде Sqids (Hashids), base62 или случайной генерации.
- **Редирект** — перенаправление пользователя с короткого URL на оригинальный с HTTP-статусом 301 (Moved Permanently) или 302 (Found).
- **Кэширование** — хранение соответствий короткий код → длинный URL в быстром хранилище (Redis, in-memory cache) для минимизации нагрузки на основную базу данных.
- **Сбор аналитики** — асинхронная запись событий перехода (IP-адрес, User-Agent, Referer, временная метка) с последующей агрегацией.
- **Геолокация (GeoIP)** — определение страны и города пользователя по его IP-адресу на основе базы данных MaxMind GeoLite2.

В данной работе реализуется полноценный сервис сокращения ссылок с открытой архитектурой, включающий все перечисленные механизмы.

## 1.2 Анализ существующих решений

На данный момент наиболее популярными сервисами сокращения ссылок являются Bitly, TinyURL и Short.io.

**Bitly** — один из старейших и наиболее известных сервисов сокращения ссылок. Предоставляет мощную аналитику: количество кликов, географию, источники трафика, временную разбивку. Поддерживает брендированные домены и кастомные короткие ссылки. API имеет ограничения на бесплатном тарифе (1000 ссылок в месяц), а передача данных о переходах стороннему сервису поднимает вопросы конфиденциальности. Исходный код закрыт.

**TinyURL** — простой бесплатный сервис без необходимости регистрации. Предоставляет минимальную аналитику (только количество кликов). Не поддерживает брендированные домены, API отсутствует. Подходит для разового использования, но не для маркетинговых кампаний, требующих детальной статистики.

**Short.io** — современный сервис с поддержкой брендированных доменов, детальной аналитикой и API. Предоставляет интеграции с популярными платформами (WordPress, Shopify). Бесплатный тариф ограничен 100 ссылками в месяц. Исходный код закрыт, данные передаются стороннему сервису.

## 1.3 Постановка задачи

В рамках данной курсовой работы поставлена следующая задача:

Разработать высокопроизводительный сервис сокращения ссылок на языке Go, реализующий следующий функционал:

- Создание коротких ссылок через REST API с валидацией входного URL (схема http/https).
- Редирект с короткого кода на оригинальный URL с HTTP-статусом 301 Moved Permanently.
- Сбор аналитики переходов: IP-адрес, User-Agent, Referer, временная метка.
- Геолокационное обогащение событий (определение страны и города по IP через GeoLite2).
- Асинхронная обработка click-событий через буферизированный канал с batch-вставкой в БД.
- Кэширование разрешённых коротких кодов в Redis с автоматическим in-memory fallback.
- Автоматические миграции базы данных при запуске приложения.
- Graceful shutdown с дообработкой очереди событий.
- HTML-дашборд для визуального тестирования API.
- In-memory fallback для всех внешних зависимостей (PostgreSQL, Redis, GeoIP).
- Контейнеризация через Docker (многостадийная сборка) и Docker Compose.

## 1.4 Требования к программному продукту

### Функциональные требования

- **FR-1**: Сервис должен предоставлять REST API для создания короткой ссылки (`POST /api/v1/shorten`).
- **FR-2**: Сервис должен валидировать входной URL (проверка формата и схемы http/https).
- **FR-3**: Сервис должен генерировать уникальный короткий код на основе числового ID записи с использованием алгоритма Sqids.
- **FR-4**: Сервис должен генерировать UUIDv4 management token для каждой созданной ссылки.
- **FR-5**: Сервис должен выполнять редирект 301 Moved Permanently при переходе по короткому коду (`GET /:code`).
- **FR-6**: Сервис должен собирать аналитику переходов: IP-адрес, User-Agent, Referer.
- **FR-7**: Сервис должен определять страну и город по IP-адресу через GeoLite2 базу MaxMind.
- **FR-8**: Сервис должен предоставлять агрегированную аналитику по короткой ссылке (`GET /api/v1/analytics/:code?token=<management_token>`), включая общее количество кликов, разбивку по дням, топ стран и топ рефереров.
- **FR-9**: Сервис должен кэшировать разрешённые короткие коды в Redis.
- **FR-10**: Сервис должен автоматически переключаться на in-memory реализации при недоступности PostgreSQL или Redis.
- **FR-11**: Сервис должен автоматически накатывать миграции базы данных при запуске.
- **FR-12**: Сервис должен предоставлять HTML-дашборд для тестирования API (`GET /dashboard`).
- **FR-13**: Сервис должен корректно завершать работу по сигналу SIGINT/SIGTERM с дообработкой очереди событий.

### Нефункциональные требования

- **NFR-1**: Сервис должен быть реализован на языке Go (версия 1.26).
- **NFR-2**: В качестве веб-фреймворка должен использоваться Fiber v2.
- **NFR-3**: В качестве СУБД должна использоваться PostgreSQL 16.
- **NFR-4**: В качестве кэша должен использоваться Redis 7.
- **NFR-5**: Сервис должен быть контейнеризован с использованием Docker (многостадийная сборка, distroless-образ).
- **NFR-6**: Инфраструктура должна запускаться одной командой через Docker Compose.
- **NFR-7**: Код должен быть покрыт модульными, интеграционными и E2E-тестами.
- **NFR-8**: Должны быть реализованы бенчмарки ключевых операций сервисного слоя.
- **NFR-9**: Должен быть настроен статический анализ кода (golangci-lint).
- **NFR-10**: Должно быть настроено сканирование безопасности (gosec) и проверка уязвимостей зависимостей (govulncheck).
- **NFR-11**: Должен быть настроен CI/CD пайплайн (GitHub Actions) для автоматического запуска линтинга, тестов, сканирования безопасности и сборки.
- **NFR-12**: API должно быть документировано в формате OpenAPI 3.1.
- **NFR-13**: Сервис должен использовать луковую архитектуру (Layered Architecture) с разделением на слои: handlers → service → repository.
- **NFR-14**: Обработка click-событий должна быть асинхронной, через буферизированный канал (capacity 1000) с batch-вставкой (до 50 событий или раз в 1 секунду).

## 1.5 Вывод по аналитической части

В ходе аналитического исследования была обоснована актуальность разработки собственного сервиса сокращения ссылок с открытой архитектурой. Выявлено, что существующие популярные решения (Bitly, TinyURL, Short.io) обладают закрытым исходным кодом, не позволяют развёртывать сервис на собственной инфраструктуре и требуют передачи данных о переходах стороннему сервису, что поднимает вопросы конфиденциальности и соответствия требованиям законодательства.

Определены ключевые области применения: маркетинг и реклама, социальные сети, брендинг, аналитика контента. Сформулированы ключевые механизмы работы сервиса сокращения ссылок: генерация короткого кода, редирект, кэширование, сбор аналитики, геолокация.

На основе анализа аналогов и требований к программному продукту поставлены конкретные задачи: реализация REST API для создания и разрешения коротких ссылок, асинхронный сбор аналитики с GeoIP-обогащением, кэширование через Redis с in-memory fallback, автоматические миграции БД, graceful shutdown, HTML-дашборд, контейнеризация через Docker Compose.

Сформулированы функциональные требования (13 требований), охватывающие все ключевые сценарии использования сервиса, и нефункциональные требования (14 требований), обеспечивающие производительность (асинхронная обработка, кэширование, batch-вставка), качество кода (статический анализ, тестирование, бенчмарки), безопасность (SAST-анализ, проверка уязвимостей, distroless-образ, non-root пользователь) и документирование (OpenAPI спецификация).
